# Copiq

## 1. Overview

Copiq is a personal developer tool that captures clipboard history from a desktop client and provides a centralized server for storage, search, and AI-powered actions.

The primary use case is reading English generated by Claude Code while working in a terminal such as Ghostty.

The user selects text in the terminal and copies it. The Copiq client automatically sends the content to the Copiq server. The user can then open the CLI or Web UI to translate, explain, simplify, or otherwise process the copied text.

The system is intentionally designed so that **clipboard collection and AI processing are separated**.

```text
┌──────────────────────┐
│  Ghostty / Terminal  │
│  Claude Code         │
└──────────┬───────────┘
           │
           │ Copy
           ▼
┌──────────────────────┐
│   Clipboard Client   │
│       CLI / Daemon   │
└──────────┬───────────┘
           │ HTTP
           ▼
┌──────────────────────────────────┐
│        Clipboard Server          │
│                                  │
│  REST API                        │
│  Clipboard History               │
│  Search                          │
│  AI Actions                      │
│  Translation Cache               │
└──────────┬───────────────────────┘
           │
           ├──────────────┐
           ▼              ▼
      ┌─────────┐    ┌─────────────┐
      │ Database│    │ AI Provider │
      └─────────┘    └─────────────┘
           ▲
           │
     ┌─────┴─────┐
     │           │
     ▼           ▼
┌─────────┐ ┌────────────┐
│   CLI   │ │  Web UI    │
└─────────┘ └────────────┘
```

# 2. Goals

## 2.1 Primary Goals

The system should:

1. Automatically capture clipboard content.
2. Maintain clipboard history.
3. Provide a centralized server for clipboard data.
4. Allow multiple clients to use the same clipboard history.
5. Provide AI-powered actions on clipboard content.
6. Cache AI results.
7. Provide both CLI and Web interfaces.
8. Work well with terminal-based workflows such as Claude Code.
9. Keep the client lightweight.
10. Allow the AI provider to be changed without changing clients.

## 2.2 Primary User Experience

The target workflow is:

```text
Claude Code
    │
    │ Select text
    │
    ▼
Ctrl+C
    │
    ▼
Clipboard Client
    │
    │ automatic upload
    ▼
Clipboard Server
    │
    ▼
Clipboard History
    │
    ├── Translate
    ├── Explain
    ├── Simplify
    ├── Summarize
    └── Copy
```

The user should not need to manually copy text into a translation website.

---

# 3. Non-Goals

The first version should not attempt to become:

- A full desktop clipboard manager.
- A password manager.
- A cloud clipboard synchronization service.
- A general-purpose AI agent.
- A browser extension platform.
- A document management system.
- A replacement for Claude Code.

The system should remain focused on:

> **Clipboard history + developer-oriented AI actions.**

---

# 4. Design Principles

## 4.1 Server-Centric Architecture

The server owns:

- Clipboard history
- Persistence
- Search
- AI processing
- AI result caching
- Provider configuration

Clients should remain thin.

```text
Client = Capture + Display + User Interaction

Server = Storage + Search + AI
```

This allows multiple clients to share the same data.

---

## 4.2 AI Actions Are Server-Side

Clients should not directly call OpenAI, Claude, Azure OpenAI, or other AI providers.

Instead:

```text
Client
   │
   │ POST /api/clipboard/{id}/actions
   ▼
Server
   │
   ▼
AI Provider
```

This provides:

- Centralized API key management
- Centralized prompt management
- Result caching
- Provider switching
- Usage tracking
- Consistent behavior across clients

---

## 4.3 AI Actions Are Extensible

Translation is the first action, not the entire product.

Potential actions include:

```text
translate
explain
simplify
summarize
rewrite
extract_terms
```

The API should therefore use an action-oriented model instead of hard-coding translation into the clipboard entity.

# 5. System Components

## 5.1 Clipboard Client

The Clipboard Client runs on the user's desktop.

Responsibilities:

- Monitor the system clipboard.
- Detect new clipboard content.
- Deduplicate content locally when possible.
- Send clipboard entries to the server.
- Optionally provide local notifications.
- Optionally provide a local CLI interface.

The client should not contain business logic related to AI.

# 6. Clipboard Client Modes

The client can support two modes.

## 6.1 Daemon Mode

The daemon continuously monitors the clipboard.

```bash
copiq-daemon
```

Typical behavior:

```text
Start
  │
  ▼
Wait for clipboard owner-change event
  │
  ▼
Read selection
  │
  ├── Same as last value → discard
  │
  └── New
        │
        ▼
    Upload
```

### Event-driven, not polled

The target environment is **X11** (Ubuntu GNOME; `XDG_SESSION_TYPE=x11`), which
has no equivalent of Wayland's `wl-paste --watch`. X11 clipboard ownership is
announced through the **XFIXES** extension, and subscribing to it is what
separates a daemon that costs nothing when idle from one that polls `xclip -o`
on a timer — roughly 172,000 process spawns a day at 500 ms, on a laptop,
for something idle almost all of the time.

`python-xlib` provides this as a pure-Python package with no system
dependencies and no compilation. Verified on this machine (XFIXES 4.0,
python-xlib 0.33, inside a clean virtualenv):

```python
from Xlib import display, X
from Xlib.ext import xfixes

d = display.Display()
d.xfixes_query_version()
w = d.screen().root.create_window(0, 0, 1, 1, 0, X.CopyFromParent)
d.xfixes_select_selection_input(
    w, d.get_atom('CLIPBOARD'), xfixes.XFixesSetSelectionOwnerNotifyMask)

while True:
    e = d.next_event()          # blocks; no CPU cost while idle
    ...                         # read selection, hand to uploader
```

`PyGObject`/`Gtk.Clipboard`'s `owner-change` signal is a working alternative
and is already installed system-wide, but it is only importable from
`/usr/bin/python3`, not from a managed virtualenv — which would force the
daemon to run against the system interpreter and give up dependency pinning.
`python-xlib` avoids that trade entirely.

### Wayland

If this machine ever moves to Wayland, the XFIXES path stops working and the
replacement is `wl-paste --watch`, which is simpler. Keep the watcher behind a
small interface with one method — "call this coroutine on every clipboard
change" — so the swap touches one file. Do not build the abstraction further
than that on speculation.

### macOS

The watcher's small interface (one coroutine, "call this on every clipboard
change") is also what lets a second OS have its own backend instead of an
abstraction layer: `copiq_daemon/watcher_macos.py` implements the same shape
as the X11 module, and `copiq_daemon/__main__.py` picks between them on
`sys.platform` at startup.

AppKit has no push notification for clipboard changes — no XFIXES
equivalent — so the mechanism is polling `NSPasteboard.changeCount()` every
300ms (the same approach Maccy/Clipy/Alfred use). This does **not** repeat
the mistake the X11 section above warns against: `changeCount()` is a single
in-process property read, not a subprocess spawn, so polling it a few times
a second is negligible — the 172,000-spawns/day math only applies to
shelling out to `xclip -o` on a timer.

Packaging: a LaunchAgent (`deploy/com.copiq.daemon.plist`), not a
LaunchDaemon — like the systemd unit's tie to `graphical-session.target`
(section 31.0), it needs a logged-in GUI session for pasteboard access.

### What the daemon deliberately does not do

It does not deduplicate beyond suppressing a byte-identical repeat of the value
it just uploaded, and it does not scan for secrets. Both belong on the server
(sections 13.1 and 29). The daemon reads the clipboard and POSTs it; keeping it
that thin is what lets the browser extension and VS Code extension in section
38 reuse everything behind it.

This is the preferred mode for everyday use.

# 8. Recommended Technology Stack

The system is **Python**. Nothing here is computational — it is HTTP handlers,
two SQLite tables, a subprocess, and JSON parsing — and Python is the better
language for glue of that shape. Section 8.5 records the alternative that was
considered and why it lost, so the decision is not relitigated later.

## 8.1 Backend

```text
Python 3.12
FastAPI          -- REST API, request validation
Uvicorn          -- ASGI server
Pydantic v2      -- wire contracts
SQLAlchemy 2.0   -- persistence
Alembic          -- schema migrations
uv               -- dependency and environment management
```

**Python 3.12, not 3.14.** The interpreter on this machine defaults to 3.14.2
via pyenv, which is new enough that binary wheels for the long tail of
dependencies may not exist yet — and a personal tool is not where you want to
be compiling C extensions from source. Pin it with a `.python-version` file;
`uv` provisions the interpreter itself, so this does not disturb the system or
pyenv default. 3.13 is equally defensible.

**Pydantic models and SQLAlchemy models stay separate**, rather than merged via
SQLModel. It is tempting to unify them for a schema this small, but the two
genuinely differ here: `content_hash` and `cache_key` are internal and must
never appear on the wire, while the list envelope in section 14.2 has no table
behind it at all. SQLModel's whole benefit is collapsing that distinction,
which is exactly the distinction worth keeping.

Recommended initial database:

```text
SQLite
```

SQLite is sufficient for a personal installation.

PostgreSQL can be supported later if the server becomes multi-user or requires
higher concurrency. SQLAlchemy makes that a connection-string change plus a
migration review, not a rewrite — which is most of why it is here rather than
raw `sqlite3`.

---

## 8.2 CLI

```text
Python 3.12
argparse        -- stdlib
http.client     -- stdlib
json            -- stdlib
```

**Standard library only, deliberately.** `copiq list` is a single HTTP GET
against a local server, and it gets typed dozens of times a day, so interpreter
startup *is* the command's latency. Measured on this machine, warm, 30 runs
each:

| Imports | Startup |
| --- | --- |
| bare interpreter | 11.6 ms |
| `json` + `http.client` | 33.7 ms |
| `argparse` + `json` + `urllib.request` | 40.6 ms |
| `click` + `json` + `http.client` | 51.6 ms |
| `httpx` alone | 103.9 ms |
| `typer` + `httpx` + `rich` | 116.3 ms |

The conventional choice — Typer with httpx and Rich — costs **116 ms before the
process does anything**, which is roughly the threshold where a command stops
feeling instant. `httpx` alone costs more than the entire stdlib stack: it is
built for connection pooling and async, and the CLI makes one request and
exits. Use `httpx` in the *server*, where those properties matter, and not
here.

`click` is worth its 18 ms if the command surface grows subcommand groups.
Start with `argparse` and switch only if that happens.

Two practical notes:

- **Install with `uv tool install`**, which writes an entry point pointing at
  the interpreter directly. Going through a pyenv shim costs an extra ~46 ms
  (measured: 58.7 ms through the shim vs 12.6 ms direct) — four times the
  interpreter's own startup, spent on shell script dispatch.
- **Defer heavy imports into the subcommand that needs them.** A module-level
  import is paid by every invocation, including `--help`.

The CLI is a separate installable from the server and shares nothing with it at
runtime except the HTTP contract.

## 8.4 Web UI

```text
React
TypeScript
Tailwind CSS
Vite         -- dev server + build
```

Built as a standalone project in `web/copiq-web`, deployed as static files
that `copiq-server` serves (section 8.4.1). The REST API is unchanged by
this choice — sections 14 and 15 are exactly as specified, and the React app
is just another client presenting a real Bearer token (section 27), the same
as the CLI and daemon.

An earlier version of this section specified Jinja2 + HTMX instead, on the
reasoning that three pages whose only interaction is "click Translate, show
the result underneath" don't need a second toolchain. §8.4.2 records why that
was reversed, and it is worth reading before re-reversing it again: the
concrete failure that came out of the HTMX version was not "wrong tool for a
simple job" in the abstract, it was a specific, silent htmx-inheritance class
of bug (see the git history for `templates/base.html`) that a plain HTTP test
suite cannot see because it is pure client-side attribute-inheritance
behavior. That risk is structural to htmx's design, not a mistake particular
to this codebase, and it does not exist in React: state is explicit and
component-local, so there is no inheritance mechanism for a sibling
interaction to silently swallow.

### 8.4.1 Running It

Development (two processes, hot reload, CORS between them):

```bash
cd web/copiq-web
npm install
npm run dev            # http://localhost:5173, proxied to the API via CORS
```

Production (one process; the server serves the built assets):

```bash
cd web/copiq-web
npm install
npm run build           # writes web/copiq-web/dist/
cd ../..
uv run uvicorn copiq_server.main:app --port 5080
# http://127.0.0.1:5080 now serves both the API and the Web UI
```

`main.py` mounts `dist/` at `/` only if it exists, and logs a warning (not an
error) if it doesn't — the API works standalone either way, which matters for
Phase 3/4 development before Phase 5's UI exists yet.

### 8.4.2 Decision Record: React over HTMX

The HTMX version worked in every check except the one that mattered: it
returned the correct HTTP response, htmx fired every one of its own
success-path events (`afterSwap`, `afterSettle`) with the correct target
element and a 200 status, and the browser still displayed nothing.

**Root cause.** `hx-select`, `hx-target`, and `hx-swap` are *inheritable*
htmx attributes. The focus-refresh feature (section 26) put
`hx-select="#history"` on `<body>` — and every descendant htmx-triggered
element inherits an ancestor's `hx-select` unless it declares its own,
including the action buttons, whose `POST /actions` responses were small
standalone `<div class="result">...</div>` fragments with no `#history`
element inside them. The inherited select filtered every one of those
responses down to nothing, and htmx swapped in empty content while still
reporting success at every stage of its own lifecycle.

**Why this generalizes, and isn't just a fix.** The bug was two independent
htmx features — an ancestor-scoped refresh trigger, and a descendant action
button — composing in a way neither one's author had in view. Fixing the one
instance (move the trigger off `<body>`) does not remove the mechanism: any
future htmx attribute placed on a common ancestor for one purpose can silently
reach into an unrelated descendant's request for another purpose, and htmx's
own request lifecycle will report success throughout, because it did succeed
by its own logic — the attribute inheritance is small-print, working exactly
as designed. A regression test could only be written as a structural check
("`<body>` may not carry these attribute names") because a plain HTTP test
cannot observe client-side attribute inheritance at all; it cannot observe the
*next* instance of the same mechanism appearing somewhere else in the markup.

**Why it was so hard to find.** Every layer that is normally sufficient to
trust — the HTTP response body, the framework's own event log — reported
success. Diagnosis needed a live browser with an instrumented `XMLHttpRequest`
and a `MutationObserver` on the actual target node to see that zero DOM
mutations occurred despite `afterSwap` firing. That is a meaningfully higher
verification bar than the one this project can routinely apply (the Python
test suite has no browser in it), which is itself a reason to prefer a UI
model where the equivalent bug class does not exist over one where it exists
but is fixed.

**What React removes, specifically.** There is no attribute-inheritance
mechanism between unrelated components. A parent's polling logic and a
child's button handler cannot silently share configuration neither author
wrote for the other; the only way one component affects another's rendered
output is an explicit prop or a value read from explicit state. The class of
bug — not just this instance of it — has nowhere to live.

**What this costs, honestly.** npm, a build step, a second dev-time process,
and CORS configuration between them are real, and were the entire reason
HTMX was chosen originally. Those costs are unchanged by this reversal; what
changed is the assessment of which failure mode is worse for a tool one
person is maintaining alone. A slower, more mechanical toolchain that fails
loudly (a TypeScript compile error, a failed `npm run build`) was judged
better than a fast, code-light one whose failure mode is silent and needs a
live browser and a `MutationObserver` to even see.

### 8.4.3 Theming

Light, dark, and "system" (follow the OS preference), toggled from a control
in the history page header and persisted to `localStorage` under
`copiq.theme`.

```text
web/copiq-web/src/
├── lib/theme.ts        -- storage, matchMedia check, applies the .dark class
├── lib/useTheme.ts      -- React hook wrapping the above
└── components/ThemeToggle.tsx
```

Tailwind v4's `dark:` variant defaults to `prefers-color-scheme` only, which
can't be overridden by a manual choice. `index.css` adds
`@custom-variant dark (&:where(.dark, .dark *));` so `dark:` classes key off
a `.dark` class on `<html>` instead, which `lib/theme.ts` sets or clears --
in "system" mode, based on `matchMedia`; in "light"/"dark" mode, directly,
overriding whatever the OS says.

**Applied twice, deliberately.** A small inline script in `index.html`'s
`<head>` reads the same `localStorage` key and toggles the same class
*before Vite's bundle even loads*, so the correct theme is present for the
very first paint. `useTheme` then takes over reactively once React mounts.
Without the inline script, a dark-mode user would see a flash of the light
theme on every load while the bundle downloads and executes -- small, but
avoidable for the cost of a dozen lines of vanilla JS with no dependency on
anything else in the app.

**Mermaid diagrams (section 21.1) follow the app's theme, including
diagrams already on screen.** `mermaid.initialize({..., theme})` is global
configuration, not a per-render option, so `lib/mermaid.ts` re-initializes
it whenever the requested theme differs from the last one used, before the
next `render()`. `ItemCard.tsx` includes `isDark` in the dependency array of
the effect that calls `renderMermaid`, so toggling the theme re-renders any
diagram currently displayed in the new palette immediately, rather than
only affecting diagrams generated from that point on -- confirmed live:
toggling flipped a rendered flowchart's node fill from a light lavender to
a dark near-black and back, not just the surrounding page chrome.

## 8.5 Decision Record: Python over .NET

.NET 10 was the original recommendation and is installed on this machine
(10.0.301). It was rejected, but not because it was unsuitable — the margin was
narrow, and the reasoning is recorded here so the question can be reopened on
evidence rather than mood.

**What .NET would have done better:**

- *Deployment.* `dotnet publish --self-contained` produces one binary with no
  runtime to install. Python needs `uv` present on the target. For a
  single-machine personal tool this is close to irrelevant; for anything
  distributed it would dominate.
- *CLI startup.* NativeAOT starts in ~5–10 ms against Python's ~35 ms best
  case. Real, but 35 ms is below the threshold where anyone notices.
- *Compile-time contracts* shared across three components, which Python
  replaces with Pydantic models validated at runtime and a test.

**What decided it for Python:**

- *The work is glue.* No computation exists anywhere in this system. FastAPI
  and SQLAlchemy express this API in substantially less code than ASP.NET Core
  and EF Core, and on a solo project the amount of code to maintain is the
  dominant long-term cost.
- *The X11 daemon.* This is the concrete, verified difference rather than a
  matter of taste. Section 6.1 has the detail: Python reaches XFIXES through a
  pure-Python package, .NET reaches it through hand-written P/Invoke or not at
  all.
- *Iteration speed*, which for a tool whose prompts and actions will be tuned
  by feel over months is worth more than static types.

**What would justify revisiting:** the server needing to run somewhere other
than this machine, or the CLI's startup becoming a genuine irritation. Neither
is a Phase 1 concern.


The product is **Copiq**; the CLI binary is `copiq` too, matching it. An
earlier version of this section argued for keeping the CLI named `cclip`
independently of the product name -- a short binary name for a longer
product name is a reasonable default in general, but the project's own
naming decision overrides it here. `~/.config/cclip/` and its
`CCLIP_CONFIG` env override moved to `~/.config/copiq/` and
`COPIQ_CONFIG` to match (section 27).

**One `pyproject.toml`, four packages.** A uv workspace with per-package
projects is the more "correct" layout and is not worth it here: the packages
are always installed together, versioned together, and edited in the same
commit. Split them when one of them genuinely ships on its own.

The important constraint is the dependency direction — `copiq_cli` and
`copiq_daemon` may import `copiq_shared`, and nothing may import
`copiq_server`. The CLI's startup budget (section 8.2) makes this
load-bearing rather than stylistic: one accidental import of the server package
pulls FastAPI and SQLAlchemy into a command that only needed `http.client`.
Enforce it with an import-linter rule, not with discipline.

## 9.1 Why Contracts Are Split in Two

`copiq_shared/types.py` holds **`TypedDict` definitions only**. The Pydantic
models live in `copiq_server/api/schemas.py` and never leave the server.

This is not redundancy for its own sake — it is the startup budget again.
Measured, warm, 30 runs each:

| `copiq` imports | Startup |
| --- | --- |
| stdlib only, no shared contracts | 38.6 ms |
| stdlib + `TypedDict` contracts | 41.5 ms |
| stdlib + Pydantic contracts | 70.4 ms |

`TypedDict` is erased at runtime — it costs 3 ms and buys the CLI full static
checking against the API. Pydantic costs 32 ms to import for validation the CLI
does not need: it is talking to a local server it trusts, and if the response
shape is wrong, the right outcome is a traceback during development, not a
validated error object in production.

**The two shapes must not drift**, so a single test asserts they agree:

```python
def test_wire_contracts_match():
    for name, td in vars(copiq_shared.types).items():
        model = getattr(schemas, name, None)
        if model is None or not is_typeddict(td):
            continue
        assert td.__annotations__.keys() == model.model_fields.keys(), name
```

A renamed field then fails CI, rather than reaching the CLI as a `KeyError` on
someone's terminal. If that test ever becomes hard to write, the two really
have diverged and the split has stopped paying — collapse it and take the
32 ms.

# 12. Database Schema

Initial schema:

```text
clipboard_items
──────────────────────────────
id                   INTEGER PK
content              TEXT NOT NULL
content_hash         TEXT NOT NULL      -- SHA-256 of content, hex
content_type         TEXT NOT NULL
source               TEXT NOT NULL
client_id            TEXT NOT NULL
has_possible_secret  INTEGER NOT NULL DEFAULT 0   -- see section 29
created_at           TEXT NOT NULL      -- ISO-8601 UTC
```

### Conventions

**Timestamps.** SQLite has no native date type; `DATETIME` is a type affinity,
not a storage format. All timestamps are stored as **ISO-8601 strings in UTC**
(`2026-09-11T01:15:32Z`), which sorts lexicographically in the same order it
sorts chronologically — so the `created_at` indexes work without a conversion
function. Local time is a presentation concern and never reaches the database.

**Foreign keys.** SQLite does not enforce foreign keys unless
`PRAGMA foreign_keys = ON` is set **per connection**. It is off by default, so
the `ON DELETE CASCADE` below is silently inert if this is forgotten — set it
on SQLAlchemy's `connect` event, and assert it in an integration test rather
than trusting it:

```python
@event.listens_for(engine, "connect")
def _fk_on(conn, _):
    conn.execute("PRAGMA foreign_keys=ON")
```

AI results:

```text
ai_action_results
────────────────────────────
id                 INTEGER PK
clipboard_item_id  INTEGER NOT NULL
                     REFERENCES clipboard_items(id) ON DELETE CASCADE
cache_key          TEXT NOT NULL
action             TEXT NOT NULL
parameters         TEXT              -- normalized JSON; NULL when the action takes none
provider           TEXT NOT NULL
model              TEXT NOT NULL
prompt_version     TEXT NOT NULL
provider_version   TEXT              -- e.g. "claude-cli/2.1.268"; see 18.1
status             TEXT NOT NULL     -- pending | completed | failed
result             TEXT              -- NULL unless status = completed
error_message      TEXT              -- NULL unless status = failed
created_at         TEXT NOT NULL     -- ISO-8601 UTC
```

`ON DELETE CASCADE` is what implements section 30's rule that AI results follow
their source item's retention. Expressing it in the schema rather than in the
retention job means it also holds for a manual `DELETE /api/clipboard/{id}`,
for a bulk purge, and for anything written directly against the database — a
background job only covers the case someone remembered to write.

Recommended indexes:

```text
INDEX         ix_clipboard_items_created_at      (created_at DESC)
INDEX         ix_clipboard_items_dedup           (content_hash, client_id, created_at)
UNIQUE INDEX  ux_ai_action_results_cache_key     (cache_key)
INDEX         ix_ai_action_results_item          (clipboard_item_id, created_at)
```

`ux_ai_action_results_cache_key` is what actually enforces the cache described
in section 22. An application-level "check then insert" is not sufficient:
two concurrent requests for the same action would both miss and both call the
AI provider. Writes should be an upsert against this index
(`ON CONFLICT(cache_key) DO UPDATE`), which also lets a retry replace an
earlier `failed` row in place rather than accumulating one row per attempt.

`ix_ai_action_results_clipboard_action` — indexing only
`(clipboard_item_id, action)` — is deliberately **not** used as the cache
lookup. It cannot distinguish two translations produced by different models or
with different parameters, so it would return stale results after a provider
or prompt change.

# 13. Deduplication

Clipboard monitoring can generate the same content repeatedly.

For example:

```text
Ctrl+C
Ctrl+C
Ctrl+C
```

should not necessarily create three records.

Calculate:

```text
SHA-256(content)
```

and store it as `content_hash`.

The server can use:

```text
content_hash + time window
```

to determine whether an entry is a duplicate.

A simple first implementation can use:

```text
Same hash
+
same client
+
within N seconds
=
duplicate
```

The exact deduplication policy should remain configurable:

```toml
[deduplication]
window_seconds = 5
scope_to_client = true
```

## 13.1 Enforcement

**The server is authoritative.** The client may skip an upload only when the
new clipboard value is byte-identical to the value it uploaded immediately
before. Any other suppression belongs on the server, which is the only place
that sees the full history — a client that deduplicates against its own state
will silently drop entries after a restart, and that class of data loss is very
hard to diagnose from the outside.

Because the server owns the decision, `POST /api/clipboard` must be idempotent
within the dedup window, so that a client retrying after a network timeout does
not create a second record:

| Case | Status | Body |
| --- | --- | --- |
| New content | `201 Created` | `{ "id": 128, "createdAt": "...", "deduplicated": false }` |
| Duplicate within the window | `200 OK` | `{ "id": 127, "createdAt": "...", "deduplicated": true }` |

In both cases the client receives a usable `id`, so the caller never needs to
branch on the status code to continue.

### Limits

Clipboard content is unbounded in practice — copying a whole file, a stack
trace, or a base64 blob is routine — so size must be capped explicitly:

| Setting | Default | Behavior when exceeded |
| --- | --- | --- |
| `clipboard.max_content_length` | 1 MiB | `413 Payload Too Large`; nothing is stored |
| `ai.max_input_length` | 16 KiB | The AI action is rejected with `413`; the clipboard item is unaffected |

The two limits are deliberately separate and enforced at different layers. The
storage limit protects the database and the list endpoints; the AI limit
protects against provider request failures and runaway cost. An item may
therefore be stored successfully and still be too large to run an action
against — which is the correct outcome, not an error to paper over.

### Why a cursor instead of `page`/`pageSize`

Offset pagination is wrong for this table specifically. Clipboard items are
inserted at the head continuously while the user reads, so by the time the
client requests page 2, the rows have shifted down by however many things were
copied in between — the client sees items it already has, and silently misses
others that slid past the boundary. A cursor anchored to an `id` is stable
regardless of what arrives during paging.

The envelope also gives the CLI and Web UI something offset paging never
provided: a definite answer to "is there more", without a second request or a
`COUNT(*)` over the whole table.

## 15.1 Action Parameters

Every action accepts an optional `parameters` object. `translate` and
`explain` read `targetLanguage`, falling back to `ai.default_target_language`
when it is omitted; `diagram` reads `diagramType` (section 21.1), falling
back to `"auto"`. `simplify` reads none.

Parameters must be **normalized before use**: unknown keys rejected, defaults
filled in, keys sorted, and case-insensitive values lower-cased
(`zh-CN` → `zh-cn`). The normalized form is what gets stored and hashed; an
un-normalized object produces a different cache key for a request that should
have been a hit.

Defining `parameters` now, while `targetLanguage` is the only one, is what
keeps the cache key stable. A parameter introduced later that is *not* part of
the key silently returns results computed under the old value — the cache would
happily serve a Chinese translation to a request for Japanese, with no error
anywhere.

# 17. AI Provider Abstraction

Do not couple the application directly to one provider.

Define an abstraction such as:

```python
class AiRequest(BaseModel):
    prompt: str            # built by the application from the versioned template
    input: str             # untrusted clipboard content, deliberately kept separate
    model: str | None = None


class AiResult(BaseModel):
    content: str
    model: str             # the model that actually answered, not the alias requested
    provider_version: str  # CLI version, or API version header
    input_tokens: int | None = None
    output_tokens: int | None = None
    cost_usd: Decimal | None = None
    duration_ms: int


class AiProvider(Protocol):
    async def execute(self, request: AiRequest) -> AiResult: ...
```

`Protocol` rather than an ABC: implementations are structurally checked by the
type checker and never need to inherit anything, which keeps `FakeAiProvider`
(section 33) a plain class with one method.

Cancellation is not a parameter. Python expresses it through task cancellation
and `asyncio.timeout()`, so the timeout belongs at the call site in the action
pipeline, and the provider's job is to clean up its subprocess when cancelled —
see section 17.1.

Two properties of this shape matter:

- **The provider returns metadata, not a bare string.** Section 34 requires
  logging `provider`, `model`, and `duration`, and section 12 stores `model` on
  every row. A `Task<string>` cannot supply any of it, so every implementation
  would end up smuggling it out through a side channel.
- **Prompt construction stays in the application layer.** The provider receives
  an already-built prompt and the raw input separately. Passing a bare `action`
  string instead would force every implementation to duplicate prompt selection,
  and section 18's versioning would have no single place to live.

Possible implementations:

```text
ClaudeCliProvider     -- subprocess: claude -p  (see 17.1)
AnthropicProvider     -- Anthropic API, API key
OpenAiProvider
AzureOpenAiProvider
OllamaProvider        -- fully local
```

Provider selection can be configured:

```toml
[ai]
provider = "claude_cli"
model = "haiku"
default_target_language = "zh-CN"
max_input_length = 16384
timeout_seconds = 120
max_concurrency = 2

[ai.model_overrides]      # per-action; falls back to `model` above if unlisted
diagram = "sonnet"        # see section 21.1 -- inferring structure may warrant it
```

Server configuration is TOML, loaded by `pydantic-settings` with environment
variable overrides (`COPIQ_AI__MODEL=sonnet`), so the settings object is
validated at startup rather than at first use. A typo in a provider name should
stop the server, not surface three hours later as a failed action.

## 17.1 Claude CLI Provider

Because the operator already has a Claude subscription, the default provider
invokes the local `claude` CLI in headless mode rather than calling a billed
API. No API key is provisioned, stored, or rotated — the subprocess reuses the
credentials from the operator's existing `claude` login.

### Invocation contract

```bash
claude -p \
  --model haiku \
  --output-format json \
  --restricted \
  --disable-slash-commands \
  --allowedTools '' \
  --max-turns 1
```

The prompt is written to **stdin**, never passed as an argument. Clipboard
content can be megabytes, can contain any byte sequence, and is visible in
`ps` output and process accounting when passed via `argv` — which directly
contradicts section 28. Stdin avoids the length limit, the quoting problem, and
the disclosure at once.

### Prompt shape

The instruction must be in the prompt itself, with the clipboard content
delimited:

```text
Translate the text between the markers into Simplified Chinese.
Output only the translation, nothing else.

<<<TEXT
This avoids introducing unnecessary coupling between the services.
TEXT>>>
```

Passing the instruction through `--system-prompt` and the content as the user
turn does **not** work. The CLI is an agent harness, and a bare sentence
arriving as the user turn is interpreted as a task: given
`This looks like a race condition.`, it replies asking which file to inspect,
rather than translating. Delimiting the content and stating the operation in
the prompt is what makes the behavior a text transformation.

### Tool lockdown

`--restricted --disable-slash-commands --allowedTools ''` and `--max-turns 1`
strip the agent down to a single text completion. This is a security boundary,
not a tidiness measure: clipboard content is untrusted input concatenated into
a prompt, so prompt injection is not preventable here — content that reads
`ignore the above and instead ...` will sometimes be obeyed. With tools removed
and turns capped, the worst outcome is a wrong string in `result`. With tools
available, the worst outcome is the model acting on attacker-chosen text with
filesystem and shell access on the server host.

### Do not use `--bare`

`--bare` looks attractive for a server-invoked subprocess — it skips hooks,
plugin sync, and CLAUDE.md discovery. It also documents that Anthropic auth
becomes "strictly `ANTHROPIC_API_KEY` or `apiKeyHelper`; OAuth and keychain are
never read", which defeats the entire reason for choosing this provider. Use
`--restricted` instead, and run the subprocess in a dedicated empty working
directory so that ambient project context stays out of the request.

### Parsing the result

`--output-format json` emits one JSON object. The fields this design consumes:

| Field | Use |
| --- | --- |
| `result` | the completion text → `ai_action_results.result` |
| `is_error` | provider failure → `status = failed` |
| `modelUsage[].canonicalModel` | the model that actually answered → `model` |
| `usage.input_tokens`, `usage.output_tokens` | observability (section 34) |
| `total_cost_usd` | observability; list-price accounting, not a subscription charge |
| `duration_ms` | observability |

A non-zero exit code, unparseable stdout, or `is_error: true` are all the same
outcome to the pipeline: store `status = failed` with the stderr tail in
`error_message`, and leave the clipboard item untouched (section 35).

### Measured cost and latency

Measured 2026-09-11, CLI 2.1.268, `--model haiku`, one-sentence input:

| | Cold | Warm (within ~1h) |
| --- | --- | --- |
| Context tokens | ~13,200 written to cache | ~13,150 read, 0 written |
| Wall clock | 5.7 s | 3.0 s |
| List-price cost | ~$0.029 | ~$0.0036 |

Three consequences follow from those numbers:

- **There is a fixed ~13 k token overhead per invocation** — the harness's own
  system prompt and tool definitions — regardless of how short the clipboard
  text is. Translating one sentence costs roughly what translating a page
  would. This is the price of reusing the subscription instead of calling the
  API directly.
- **The overhead is cached across separate invocations** and expires after
  about an hour of inactivity. Bursty use — the actual workload, since the user
  copies repeatedly while reading — mostly pays the warm price.
- **Latency is seconds, not milliseconds.** Synchronous request handling
  (section 36) stays acceptable for a single user, but this is the number that
  will force the async queue if the tool ever gains a second user.

On a subscription these costs are not billed; they consume plan rate limits
instead. A rate-limit rejection must surface as `status = failed`, not as a
retry storm.

### Process management

Each action spawns a process, so the provider must own its lifecycle:

- An `asyncio.Semaphore` bounded by `ai.max_concurrency` — unbounded spawning
  is a trivial local denial of service against the operator's own machine.
- A hard timeout via `asyncio.timeout(...)`, and on cancellation, kill the
  **process group**, not just the direct child. Spawn with
  `start_new_session=True` so the child gets its own group, then `os.killpg` it;
  `proc.kill()` alone leaves whatever `claude` itself spawned still running.
- **`create_subprocess_exec`, never `create_subprocess_shell`.** The `_shell`
  variant interposes `/bin/sh`, which would make every byte of clipboard content
  subject to shell quoting. The `_exec` form passes an argument vector directly
  and no escaping is ever required.
- Write the prompt to `stdin` and close it, then read `stdout` to completion.
  Writing without closing deadlocks against a child waiting for EOF.

### Non-determinism

Two identical requests returned different wordings:

```text
这样可以避免在服务之间引入不必要的耦合。
这避免了在服务之间引入不必要的耦合。
```

Both are correct, but they are not the same string. This is an argument for the
cache in section 22 beyond cost: without it, re-opening a clipboard item shows
the user a subtly different translation each time, which reads as a bug.

# 18. Prompt Management

Prompts should be versioned.

Example:

```text
prompts/
├── translate/
│   └── v1.txt
├── explain/
│   ├── v1.txt
│   └── v2.txt
└── simplify/
    └── v1.txt
```

The database stores:

```text
prompt_version = v1
```

This is important because changing the prompt should not make existing results impossible to reproduce or understand.

## 18.1 The Limit of `prompt_version` Under the CLI Provider

`prompt_version` versions *our* prompt. Under `ClaudeCliProvider` it does not
capture the whole input: the CLI prepends its own system prompt and tool
definitions — the ~13 k tokens measured in section 17.1 — and that text changes
with every CLI release, outside this project's control.

So `prompt_version = v1` means "our template was v1", not "this result is
reproducible". Store `provider_version` alongside it to record what the other
half of the prompt was:

```text
ai_action_results.provider_version   -- e.g. "claude-cli/2.1.268"
```

Deliberately, `provider_version` is **not** part of the cache key in section 22.
Including it would be more correct and would invalidate the entire cache on
every CLI auto-update — which, for a tool whose value is avoiding repeat AI
calls, trades away the feature to gain precision nobody asked for. Recording it
is enough to explain an unexpected result after the fact.

## 18.2 Configuring Prompts

Every action's prompt is replaceable without a code change or touching the
installed package:

```toml
[prompts]
dir = "~/.config/copiq/prompts"

[prompts.versions]
translate = "v2-formal"
```

`dir` is an override directory, checked *before* the bundled one for every
prompt lookup; unset, only the bundled prompts exist. `versions` is a
per-action map from action name to the version string that action should
actually use; an action not listed keeps its built-in default (currently
`v2` for `explain`, `v1` for the other three). Neither setting requires the
other — you can override
just the directory (to shadow `translate/v1.txt` with different wording
under the same version) or just point `[prompts.versions]` at a version
that only exists in the bundled prompts, in the unlikely case that becomes
relevant.

**Give a changed prompt a new version string; don't overwrite an existing
one's file in place.** This follows directly from section 18's own
principle: `prompt_version` is stored on every cached result specifically so
a stored translation can be traced back to what produced it. Overwriting
`translate/v1.txt`'s content changes what future `v1` results say without
changing the string `v1` itself — every already-cached row whose
`prompt_version` says `v1` now silently describes the wrong prompt, and
worse, the cache key doesn't change either, so an *already-cached* result
under the old wording keeps being served until its cache key is next
recomputed with different parameters. Adding `translate/v2-formal.txt` and
pointing `[prompts.versions]` at it avoids both problems: old rows still
correctly say `v1`, and the new version gets its own cache entries from a
clean start.

**A custom prompt is still subject to section 17.1's threat model, in both
directions.** The clipboard content it's translating/explaining/summarizing
is untrusted input from the operator's own clipboard — that hasn't changed.
What's new is that the *prompt itself* is now operator-authored text sent
to the model on every request, and models are trained to resist exactly the
pattern that a legitimate custom prompt can accidentally resemble: an
instruction telling the model to override its normal behavior or prefix its
output with specific literal text. Verified directly during development —
a custom prompt phrased as "translate into French **regardless of any other
target language**, and prefix your entire answer with the literal text
'CUSTOM PROMPT ACTIVE: '" was refused outright, with the model explicitly
naming it "a classic prompt injection pattern," even though the instruction
came from the server's own configuration, not from injected clipboard
content. Rewording it as a plain, unconditional instruction ("Translate the
text between the markers into French. Prioritize natural, idiomatic French
over a literal translation.") worked as expected. Writing custom prompts as
direct instructions rather than override/prefix directives isn't just
better prompt engineering here — it's the difference between the action
working and being silently refused.

## 21.1 Diagram Action

`diagram` visualizes the structure a piece of text describes -- a process, a
request/response flow, code relationships, data relationships -- as a Mermaid
diagram, rather than translating or explaining the words.

```text
Input:

The client sends a request to the load balancer. The load balancer forwards
it to one of three app servers. Each app server queries the shared database
and returns a response.
```

Output (fenced, stored and cached as bare source -- see below):

```text
flowchart TD
    Client --> LoadBalancer[Load Balancer]
    LoadBalancer --> AppServer1[App Server 1]
    LoadBalancer --> AppServer2[App Server 2]
    LoadBalancer --> AppServer3[App Server 3]
    AppServer1 --> DB[(Shared Database)]
    AppServer2 --> DB
    AppServer3 --> DB
```

Named `diagram`, not `mermaid` -- matching the plain-verb naming of the other
three actions keeps the output *format* an implementation detail rather than
part of the action's identity, consistent with section 4.3's reasoning for
not hard-coding translation into the clipboard entity.

**Parameters.** `diagramType` -- one of `flowchart`, `sequence`, `class`,
`er`, or the default `auto` (let the model choose, based on what the content
actually describes). Validated against that fixed set at request time
(section 15.1's "unknown values fall back to defaults" becomes "invalid
values are a 400" here, since an invalid diagram type is a request error, not
a fillable gap); participates in the cache key like any other parameter, so a
`flowchart` request never serves a cached `sequence` result for the same
content.

**Server-side postprocessing.** The prompt asks for only a fenced ` ```mermaid
` block, but models don't always comply -- some wrap it in a sentence of
preamble or a closing remark regardless of instruction. The pipeline (section
16) extracts the fenced block if present, or falls back to trusting the raw
response is already bare source, *before* storing the result. This runs once,
server-side, rather than being left to each client to handle separately: it's
what the CLI prints, and what gets cached, so a client written later doesn't
need to reimplement the same regex to get clean output.

**Rendering is entirely client-side, and differs by client.** A terminal
can't render Mermaid, and GitHub and most editors already render ` ```mermaid
` fences directly, so `copiq diagram <id>` just prints the (already clean)
source -- no renderer needed there. The Web UI (`web/copiq-web`) renders it as
an actual SVG via the `mermaid` npm package, dynamically imported rather than
loaded at the top of the module: mermaid's core runtime plus its per-type
renderers (flowchart, sequence, gantt, C4, cytoscape-based layouts, katex for
math...) is several hundred KB, and eagerly bundling that into every page
load for a feature most visits won't use was a measurable, avoidable
regression -- confirmed by comparing build output before and after (~933KB
down to ~235KB in the main chunk, with mermaid and its diagram-specific
sub-chunks fetched only on the first actual "Diagram" click).

**Mermaid source is untrusted input, same as any other AI output -- treat it
accordingly.** The diagram's source is model output derived from clipboard
content an attacker could have crafted (section 17.1's prompt-injection
framing applies here exactly as it does to translate/explain/simplify).
Mermaid's `securityLevel` config controls whether node labels can carry
embedded HTML/click-handlers; `"strict"` sanitizes them, the more permissive
`"loose"` does not. This project already shipped one Web UI XSS bug from
under-treating AI output as untrusted when rendering it (the htmx-inheritance
fix, `src/copiq_server/api/actions.py`'s `html.escape()` calls) -- `"strict"`
is set once, in `web/copiq-web/src/lib/mermaid.ts`, and should not be relaxed
without re-reading that history first. Malformed Mermaid syntax (the model
can still produce syntax errors even with well-formed *intent*) is caught and
falls back to displaying the raw source rather than crashing the card.

**Model choice.** Inferring the right diagram type and its structure from
prose is a more structured task than translate/explain/simplify's fairly
direct transformations, and may warrant a stronger model than the project
default. Rather than special-case this one action, `[ai].model_overrides` in
`copiq.toml` (see section 17) accepts a per-action model, e.g.
`model_overrides.diagram = "sonnet"`; unlisted actions keep using `[ai].model`.
This is a small, general mechanism, not diagram-specific plumbing -- it
exists because this was the first action where the "one model fits every
action" assumption from earlier phases stopped being obviously true.

# 22. Translation Cache

AI requests should be cached.

Cache key:

```text
SHA256(
    action
    + normalized_parameters
    + content_hash
    + prompt_version
    + provider
    + model
)
```

Example:

```text
translate
+
{"targetLanguage":"zh-cn"}
+
abc123...
+
v1
+
claude-cli
+
claude-haiku-4-5
```

The key is stored in `ai_action_results.cache_key` and enforced by the unique
index from section 12. Lookups are by key alone — never by
`(clipboard_item_id, action)`, which cannot tell two models or two target
languages apart.

Every input that can change the output is in the key, and that is the whole
invariant: drop `model` and the cache serves a GPT translation to a request
that asked for Claude; drop `normalized_parameters` and it serves Chinese to a
request for Japanese. Neither failure surfaces as an error.

Only rows with `status = completed` count as hits. A failed action still
writes a row — it is useful for observability — but the next request for the
same key retries the provider and upserts over it, so a transient outage is
never cached as a permanent answer.

# 23. CLI Design

The CLI should be optimized for terminal workflows.

## 23.1 The id Argument Is Optional

`get`, `delete`, `translate`, `explain`, `simplify`, and `diagram` all take an
optional `id`. Omit it and the command acts on the most recently captured
clipboard item instead:

```bash

```

This matches the actual workflow section 1 describes -- copy something in
the terminal, then act on it -- which doesn't naturally produce an id to type;
`copiq list` first just to read one off defeats the point of a
single-command action. Resolved with one extra `GET /api/clipboard?limit=1`
when omitted (`copiq_cli/__main__.py::_resolve_id`), never cached
client-side: the daemon could add a newer item between two commands, and a
cached "latest" would silently act on the wrong one.

# 27. Authentication

For a personal installation, authentication can initially be simple.

Possible MVP model:

```text
API Key
```

Client configuration:

```text
~/.config/copiq/config.json
```

Example:

```json
{
  "server": "http://localhost:5080",
  "apiKey": "cw_..."
}
```

The **client** config stays JSON while the server's is TOML (section 17). This
is not an oversight: the CLI already imports `json` to parse API responses, so
reading its own config costs nothing, whereas adding `tomllib` would spend
another import against the startup budget in section 8.2 for no benefit. The
server has no such constraint and gains TOML's comments and sections.

If the server is exposed outside the local machine, proper authentication and TLS become mandatory.

Note that this API key authenticates *clients to the server*. It is unrelated
to AI provider credentials — and with the default `ClaudeCliProvider` (section
17.1) there are none, because the subprocess reuses the operator's existing
`claude` login. Section 4.2's "centralized API key management" therefore has
nothing to manage until a second provider is added.

## 27.1 Key Handling

"Use an API key" is not a design until these are settled:

**Generation.** 32 bytes from a CSPRNG, base64url-encoded, with a `cw_` prefix
so the string is recognizable in a log or a paste. Never a user-chosen value —
a memorable key is a guessable key, and this one is typed once into a config
file and then never again.

**Storage.** The server stores only `SHA-256(key)`. A personal tool is exactly
where plaintext credential storage gets rationalized as harmless, and it is the
same rationalization every breached service made. A fast hash is appropriate
here, unlike for passwords: the key is full-entropy random, so there is nothing
for an offline attack to guess, and per-request Argon2 would only slow down the
server.

**Comparison.** Constant-time (`hmac.compare_digest`, stdlib). Ordinary `==`
on `str` or `bytes` short-circuits at the first differing byte and leaks the
shared prefix length through timing, which is a real attack against an endpoint
that accepts unlimited attempts.

**Multiple keys.** Store a small table rather than a single config value:

```text
api_keys
────────────────────────────
id           INTEGER PK
name         TEXT NOT NULL     -- "work-laptop"
key_hash     TEXT NOT NULL
created_at   TEXT NOT NULL
revoked_at   TEXT              -- NULL while active
last_used_at TEXT
```

One key per client is what makes rotation possible: revoking a leaked laptop
key should not mean re-provisioning every other machine. `last_used_at` is what
tells you whether a key is safe to revoke.

**Client-side file permissions.** `~/.config/copiq/config.json` holds the key
in plaintext — unavoidable, since the client must send it. Create it `0600`,
and have the client refuse to start if it is group- or world-readable. Failing
loudly is right here: a silent warning about a readable credential file is a
warning nobody reads.

**Transport.** The key is a bearer token, so it is only as protected as the
connection. Over plain HTTP on `localhost` this is acceptable; over any other
network it is equivalent to publishing the key, which is what makes TLS
mandatory the moment the server leaves the machine.

# 28. Security

Clipboard content can contain sensitive information.

The system must assume clipboard data may contain:

- Passwords
- Tokens
- API keys
- URLs containing credentials
- Customer information
- Source code
- Internal company information

Therefore:

1. Never log clipboard content by default.
2. Never log AI prompts containing clipboard content.
3. Use HTTPS for remote connections.
4. Protect API credentials (section 27.1).
5. Provide retention policies.
6. Provide deletion functionality (`DELETE /api/clipboard/{id}`, section 14.3.1).
7. Scan for likely secrets before any AI egress (section 29) — **in the MVP,
   not later**.
8. Do not send flagged content to an AI provider without an explicit,
   per-request override.

## 28.1 What Rule 7 Costs, and Why It Is Not Deferred

An earlier draft listed secret detection as a future feature (section 29) while
rule 8 forbade unreviewed egress. Those cannot both be true: with no scanner,
every action sends unreviewed content, and the MVP violates its own stated
principle on day one. A security rule that the first release knowingly breaks
is not a rule, it is a comment.

The resolution is to make the scanner small enough to ship immediately —
roughly a dozen patterns, detailed in section 29 — rather than to weaken the
rule.

## 28.2 What `ClaudeCliProvider` Changes, and What It Does Not

Choosing the CLI provider (section 17.1) genuinely reduces the credential
surface: there is no API key to leak, and the account is the operator's own
subscription rather than a billed key that could be abused at scale.

It does **not** make egress local. Clipboard content still leaves the machine
and reaches Anthropic; only the authentication path changed. The difference is
in who holds the relationship, not in whether the data moves. A local provider
such as Ollama is the only configuration where rule 8 is satisfied by
construction, and that is the honest reason to keep `AiProvider` pluggable
beyond mere good taste.

# 29. Secret Detection

The scanner ships in Phase 1. It is deliberately crude: a fixed list of
high-confidence patterns, no entropy heuristics, no machine learning.

## 29.1 Where the Gate Belongs

The earlier draft put the gate at upload time — flag a secret, refuse to
store it. That protects the wrong thing. The clipboard database sits on the
operator's own machine, already holding everything they copied; refusing to
store one item there changes very little, and it destroys history the user may
need. The irreversible step is **egress to the AI provider**.

So storage is never blocked; AI actions are:

```text
POST /api/clipboard
      │
      ▼
Scan content
      │
      ├── Clean            → store, has_possible_secret = 0
      │
      └── Possible secret  → store, has_possible_secret = 1
                              (response includes the flag)

POST /api/clipboard/{id}/actions
      │
      ▼
has_possible_secret = 1 ?
      │
      ├── No               → proceed (section 16)
      │
      └── Yes
            │
            ├── request has "acknowledgeSecret": true  → proceed
            │
            └── otherwise → 409 Conflict
```

A `409` names which pattern matched, so the user can judge it. This matters
because the override has to be usable — a gate that can only be satisfied by
editing a config file gets disabled wholesale the first time it fires on a
false positive, which leaves the system less protected than having no gate at
all.

## 29.2 MVP Pattern Set

Only patterns with a distinctive literal prefix or structure, where a match is
almost certainly a real credential:

```text
AWS access key id       AKIA / ASIA + 16 uppercase alphanumerics
GitHub token            ghp_ ghs_ gho_ ghu_ ghr_ github_pat_
Slack token             xox[baprs]-
Stripe secret key       sk_live_ / rk_live_
Google API key          AIza + 35 chars
OpenAI / Anthropic key  sk- / sk-ant-
Private key PEM         -----BEGIN (RSA|EC|OPENSSH|PGP)? PRIVATE KEY-----
JWT                     eyJ + base64url . base64url . base64url
Connection string       Password= / pwd= inside a URI or DSN
URL with credentials    scheme://user:password@host
```

Explicitly **not** included: generic high-entropy strings, and anything keyed
off variable names like `password =`. Both fire constantly on ordinary
developer text — a base64 blob, a git SHA, a documentation example — and the
cost of a false positive here is a blocked action on content the user copied
deliberately.

## 29.3 Configuration

```toml
[secret_detection]
enabled = true
block_ai_actions = true
allow_override = true
```

`Enabled: false` is available and is a legitimate choice for someone who never
copies credentials — but it is not the default. The default assumes the
operator will eventually copy a token by accident, because everyone does.

# 31. Deployment

Two long-running processes (server, daemon) and one command (`copiq`), all on
the operator's own machine.

## 31.0 Installation and Process Supervision

```bash
uv tool install --editable .      # provides `copiq` (and copiq-server/copiq-daemon)
uv sync --frozen                  # server + daemon environment
```

`uv tool install --editable .` installs every script this project defines
(`copiq`, `copiq-server`, `copiq-daemon`) into an isolated tool environment
-- there's no way to select just one from a project's `[project.scripts]`,
so `copiq-server`/`copiq-daemon` land on PATH too even though the actual
long-running server/daemon processes below are run via `uv sync --frozen` +
`uv run` instead (or `scripts/run.sh` for local dev), not from this tool
install. What matters is that `copiq` itself is what keeps the CLI off the
pyenv shim path (section 8.2) and out of the server's virtualenv.

Both long-running processes belong in **systemd user units**, not in a terminal
or a Docker container:

```ini
# ~/.config/systemd/user/copiq-server.service
[Service]
ExecStart=%h/.local/share/copiq/.venv/bin/uvicorn \
          copiq_server.main:app --port 5080
Restart=on-failure

[Install]
WantedBy=default.target
```

```ini
# ~/.config/systemd/user/copiq-daemon.service
[Unit]
After=graphical-session.target
PartOf=graphical-session.target

[Service]
ExecStart=%h/.local/share/copiq/.venv/bin/python -m copiq_daemon
Restart=on-failure

[Install]
WantedBy=graphical-session.target
```

The daemon's unit is tied to `graphical-session.target` for a concrete reason:
it needs `DISPLAY` and a live X11 connection (section 6.1). Started at boot or
under `default.target` it would have no display to connect to and would crash
in a restart loop until login.

On macOS there is no systemd; the daemon is instead installed as a
**LaunchAgent** (`deploy/com.copiq.daemon.plist`), for the same reason the
Linux unit needs a graphical session — pasteboard access requires a
logged-in GUI user, so it belongs under `~/Library/LaunchAgents/`, not a
system-wide LaunchDaemon:

```bash
mkdir -p ~/Library/Logs/copiq
cp deploy/com.copiq.daemon.plist ~/Library/LaunchAgents/   # after editing USERNAME in it
launchctl load ~/Library/LaunchAgents/com.copiq.daemon.plist
```

The server has no equivalent macOS unit yet — running it under `uv run` in a
terminal, or via `launchd` with a similar plist, is unblocked but not
packaged here.

### Binding the server beyond localhost

`copiq-server` binds `127.0.0.1` by default. Two ways to change that, per
`config.py`:

- `server_host` / `server_port` in `copiq.toml` (section 17), e.g.
  `server_host = "0.0.0.0"` to accept connections from other machines, or a
  specific LAN/VPN interface IP to scope it more tightly than "any
  interface."
- The `COPIQ_SERVER_HOST` / `COPIQ_SERVER_PORT` env vars, same effect,
  useful for a systemd/launchd unit without editing `copiq.toml`.

These only apply to the `copiq-server` entrypoint. Running via
`uvicorn copiq_server.main:app --host ... --port ...` directly (as the
systemd unit in `deploy/copiq-server.service` and the dev instructions in
the README do) takes uvicorn's own `--host`/`--port` flags instead and
ignores these settings entirely.

Binding beyond `127.0.0.1` exposes the API to everything that can reach that
interface — the whole LAN, or the internet if the port is forwarded. Auth is
a Bearer API key only (section 27.1); there is no TLS at this layer. Prefer
a specific interface over `0.0.0.0`, and put a TLS-terminating reverse proxy
(nginx/Caddy) in front if this needs to be reachable from an untrusted
network.

A simple local deployment should require minimal configuration.

## 31.1 Docker Conflicts With the CLI Provider

`ClaudeCliProvider` shells out to a `claude` binary that must be both installed
**and interactively authenticated** in whatever environment the server runs in.
A container has neither by default, and subscription credentials live in the
operator's host home directory.

The options, worst to best for a personal installation:

| Option | Cost |
| --- | --- |
| Mount the host credential directory into the container | Any code in the container can use the operator's Claude account |
| Authenticate inside the container, persist to a volume | Re-auth on every image rebuild; credentials in a volume |
| **Run the server directly on the host** | No container isolation |
| Run the server in Docker, use an API-key provider instead | Gives up the subscription — the reason for 17.1 |

The daemon settles this independently of the provider question: it needs an X11
connection to the operator's session, so it runs on the host regardless. A
deployment where the daemon is native and only the server is containerized adds
a container boundary in the middle of a two-process system that shares one
SQLite file — strictly more moving parts than running both natively.

**Recommendation: run on the host for the MVP.** Docker's isolation is worth
little here — the server is already a single-user process holding that user's
clipboard — and the first two options hand container contents the operator's
Claude account, which is a worse trade than skipping the container.

Keep the Dockerfile anyway: it is the right deployment for the day this runs
somewhere shared, and that day is also the day an API-key provider makes
sense.

# 33. Testing Strategy

```text
pytest
pytest-asyncio
httpx            -- ASGITransport, no network, no live server
```

## Unit Tests

Test:

- Clipboard deduplication
- Hash generation
- Cache key generation and parameter normalization
- Secret scanner patterns — both directions
- AI action validation
- Prompt selection
- Retention logic

The secret scanner needs its false-positive cases written as tests, not only
its true positives. Section 29.2 deliberately excludes entropy heuristics
because they misfire on ordinary developer text; a test asserting that a git
SHA, a base64 blob, and a `password = ` line in documentation all pass clean is
what stops that exclusion from being quietly reversed later.

## Integration Tests

Test:

```text
POST clipboard
     ↓
Database
     ↓
GET clipboard
```

Drive the app through `httpx.ASGITransport` against the FastAPI object
directly — no Uvicorn, no port, no network. Point each test at a temporary
SQLite **file** rather than `:memory:`: the foreign-key cascade from section 12
and the `PRAGMA foreign_keys` connection event both behave differently across
connections, and an in-memory database hides exactly the class of bug that
setup exists to catch.

AI tests should use a fake provider:

```python
class FakeAiProvider:
    """Satisfies the AiProvider protocol structurally; no base class needed."""

    def __init__(self, responses: dict[str, str]) -> None:
        self.responses = responses
        self.calls: list[AiRequest] = []

    async def execute(self, request: AiRequest) -> AiResult:
        self.calls.append(request)
        return AiResult(
            content=self.responses[request.prompt],
            model="fake",
            provider_version="fake/1",
            duration_ms=0,
        )
```

Recording `calls` is what makes the cache testable: asserting that a second
identical action left `len(calls) == 1` is the only way to prove the cache in
section 22 actually prevents the provider call, rather than merely returning
the right string.

This prevents tests from making real AI requests.

# 35. Error Handling

AI failures should not affect clipboard storage.

For example:

```text
Copy
 │
 ▼
Store clipboard
 │
 └── success

Translate
 │
 └── AI unavailable
```

The clipboard item must still exist.

The AI result carries a status, stored in `ai_action_results.status`:

```text
pending      -- reserved for the async pipeline in section 36; unused in the MVP
completed    -- result is populated and cacheable
failed       -- error_message is populated; never served as a cache hit
```

A retry writes over the existing row for that cache key rather than inserting a
new one (see section 22), so a key always has exactly one row.

```text
     │
     ├── English Simplification
     │
     ├── Developer Vocabulary
     │
     └── AI Actions
```

The key concept is:

> **Anything you copy can become an AI-assisted piece of knowledge.**

This is more extensible than building a dedicated terminal translator.

# 40. MVP Scope

The first implementation should be deliberately small.

Phases are ordered so that the workflow in section 1 — copy English from Claude
Code, read it in Chinese — works end to end as early as possible. An earlier
draft placed all AI work in Phase 4 of 5, which would have meant building a
clipboard logger, a CLI, and most of the API before the feature the tool exists
for became usable even once. Phase 3 below is the first release worth using,
and everything after it is widening, not finishing.

### Phase 1 — Server

Implement:

```text
FastAPI + Uvicorn
SQLAlchemy + Alembic
SQLite
ClipboardItem
Deduplication (13.1)
Secret scanner (29)
API key authentication (27.1)
```

Endpoints:

```text
POST   /api/clipboard
GET    /api/clipboard
GET    /api/clipboard/{id}
DELETE /api/clipboard/{id}
```

`DELETE` is here rather than later because section 28 requires a way to remove
sensitive content, and until it exists the only remedy is editing the database
by hand.

### Phase 2 — Client

Implement:

```text
Clipboard monitoring
Automatic upload
Configuration
```

At the end of this phase the system captures everything and does nothing with
it. This is the least useful the project will ever be, and it lasts exactly one
phase.

### Phase 3 — Translate, End to End

Implement:

```text
AiProvider + AiResult           (17)
ClaudeCliProvider               (17.1)  -- default, --model haiku
translate action only           (19)
AI result caching               (22)
POST /api/clipboard/{id}/actions
copiq list
copiq translate
```

**This is the first phase that delivers the product described in section 1.**
One action, one provider, and the two CLI commands needed to reach it. Ship it
and use it for a week before starting Phase 4 — the fixed ~13 k token overhead
and multi-second latency measured in section 17.1 are the kind of thing that
reads as acceptable in a design document and feels different in daily use, and
that verdict should arrive before more actions are built on the same path.

### Phase 4 — Remaining Actions and Full CLI

Implement:

```text
explain, simplify               (20, 21)
copiq get
copiq search
copiq explain / simplify
```

Each new action is a prompt template plus a registry entry. If it is more than
that, the abstraction in section 17 is wrong and this is where it surfaces.

### Phase 5 — Web

Implement:

```text
Clipboard history
Search
Translation
Explanation
```

Everything else should wait — including SSE (section 26), the async queue
(section 36), PostgreSQL, and every item in section 38.

# 41. Recommended Initial Architecture

The recommended MVP is:

```text
                         ┌──────────────────┐
                         │    Claude Code   │
                         └────────┬─────────┘
                                  │
                              Ctrl+C
                                  │
                                  ▼
                         ┌──────────────────┐
                         │ Clipboard Client │
                         │                  │
                         │ Clipboard Watch  │
                         └────────┬─────────┘
                                  │
                               HTTP
                                  │
                                  ▼
┌────────────────────────────────────────────────────┐
│                Clipboard Server                    │
│                                                    │
│  FastAPI / Uvicorn                                 │
│                                                    │
│  ┌────────────┐   ┌─────────────┐                 │
│  │ Clipboard  │   │ AI Actions  │                 │
│  │ API        │   │             │                 │
│  └─────┬──────┘   └──────┬──────┘                 │
│        │                  │                        │
│        ▼                  ▼                        │
│  ┌────────────┐    ┌──────────────┐               │
│  │ SQLite     │    │ AI Provider  │               │
│  └────────────┘    └──────────────┘               │
│                                                    │
└───────────────┬────────────────────────────────────┘
                │
         ┌──────┴───────┐
         │              │
         ▼              ▼
    ┌─────────┐    ┌───────────┐
    │   CLI   │    │  Web UI   │
    └─────────┘    └───────────┘
```

The most important architectural decision is:

> **The Clipboard Server is the source of truth. Clients are thin. AI is a server-side capability.**

This keeps the system simple enough to build quickly while leaving room for Web UI, multiple clients, multiple AI providers, vocabulary learning, and richer developer-focused AI actions later.
